# 车队日志策略业务边界检查

对 `internal/fleetlog` 及其 gateway 入口做业务规则审计。只读检查，直接给出证据与修复建议，不修改代码。

## 输入

- 待检查版本：分支名 + 提交哈希（缺省为当前工作区）。
- 需求来源：`docs/task-09/requirements.md`（第 5、6、9 节）与题面规则 1–8。
- 变更范围：`git diff --stat <base>...HEAD` 与新增文件列表。

缺少需求文档或代码无法 `go build ./...` 时，直接输出 `BLOCKED` 并说明原因，不做猜测性结论。

## 执行步骤

1. 读取需求文档与 `AGENTS.md` 第 2 节，建立 R-01～R-10 检查基线。
2. 用 `git diff --stat` 确认本次涉及的文件，只检查受影响路径及其依赖；未受影响的分组标注"未变更，沿用上次结论"。
3. 按下列 A–H 组逐组取证。每组至少给出一处 `文件:行` 或命令输出。
4. 对每组执行对应测试：`go test ./internal/fleetlog/... -run <相关用例> -race -count=1`；无用例则记 `FAIL（缺测试）`。
5. 汇总为检查表并给出总体结论。

### A 组：审批权限（R-01）

- 提交与审批是否都从会话身份取 `userID`，而非请求体字段。
- 是否存在 `approverID == requesterID` 的显式拒绝分支，且发生在写库之前。
- 已批准申请的参数是否锁定：查找更新路径是否在校验状态后才允许写。
- 退回后重提是否生成新版本并保留旧记录。

取证：搜索 `RequesterID`、`ApproverID`、`status ==`、`Pending`、`Rejected`；检查 handler 是否直接接收 `user_id` 参数。

### B 组：批次与推广（R-02、R-03、R-04）

- 创建活动时是否校验"同车队无未结束活动"，校验与写入是否在同一事务。
- 试点车是否恰为 2 台且互不重复；剩余 3 台是否未产生任何发布记录。
- 推广入口的前置条件是否为"2 台试点均为当前版本 success"，而不是"已下发"。
- 是否存在绕过推广校验的直调路径（handler/service 是否可被直接调用）。

取证：搜索 `pilot`、`promote`、`pilot_passed`、`not_released`、`count(`；用 SQL 或调试接口确认未发布车辆无 release 记录。

### C 组：版本与生效值（R-05）

- 车辆版本是否按车独立递增，生成是否在事务内、是否有唯一索引 `(vehicle_id, version)`。
- 期望值（当前版本 interval）与生效值（最后被接受的成功回执）是否分列保存，页面是否区分展示。
- 是否存在"下发即写生效值"的路径（这是最常见的误判）。
- 基线值是否在活动创建时快照并持久化。

取证：检查 repo 的 `Save`/`CreateRelease`、`UpdateEffective` 调用点；确认 `effective_interval` 只在回执被接受后写入。

### D 组：回执判定（R-06）

按需求文档 5.5 逐条核对判定顺序，必须全部覆盖：

1. 凭证车辆 ≠ 回执车辆 → 拒绝并记录；
2. 该车从未发布该版本 → 拒绝并记录；
3. 版本 < 当前期望版本 → 拒绝并记录；
4. 当前版本已有成功回执 → 重复，不重复记账；
5. 当前版本成功 → 更新生效值；
6. 当前版本失败 → 记录原因，生效值不变。

取证：寻找统一的 `judgeAck`/`applyAck` 入口；若判定散落在多个 handler，直接判 `FAIL（判定未收敛）`。

### E 组：超时与迟到（R-07）

- 超时阈值是否可配置（默认 60 秒），时间是否来自注入的 Clock。
- 超时是否既可通过定时扫描落库，也可在读取时计算，二者结果是否一致。
- 当前版本迟到成功是否更新状态并保留超时事件，而不是删除超时记录。
- 已停止活动收到迟到回执时，是否只改逐车结果、不改变活动状态。

取证：搜索 `timeout`、`Clock`、`time.Now`（业务包内直接调用计 `FAIL`）。

### F 组：停止与恢复（R-08、R-09）

- 停止是否只关闭未发送部分；已发/未发范围是否可查询。
- 页面与接口是否存在"已撤销/已恢复"等错误表述。
- 恢复对象是否仅为曾发布车辆；恢复版本是否高于该车当前版本；目标是否为基线值。
- 恢复完成后原有发布与回执记录是否仍可查。

取证：搜索 `stop`、`restore`、`baseline`、`void`；检查状态机是否允许从 `stopped` 直接跳 `restored`。

### G 组：核查与完成（R-10）

- 逐车核查是否包含：基线、期望值、生效值、状态、失败原因、下发时间、回执时间、是否迟到。
- "标记完成"是否要求 5 台当前版本全部成功；"恢复完成"是否要求全部需恢复车辆确认。
- 汇总数字与逐车明细是否可互相校验（已发数 ≠ 生效数时必须分别展示）。

取证：读取核查查询与页面模板，手工累加核对一次。

### H 组：幂等与并发

- 重复点击试点、推广、停止、恢复是否幂等（不重复生成版本）。
- 并发下发同一车辆时版本是否可能重复；是否有唯一约束或行锁兜底。
- 回执重复投递时是否只有一条计入统计。
- 是否执行过 `go test -race`，有无数据竞争报告。

## 输出格式

```markdown
## 业务边界检查结论：PASS / FAIL / BLOCKED

检查版本：<branch>@<commit>
需求版本：docs/task-09/requirements.md v<版本>

| 组 | 检查项 | 期望 | 实际证据 | 结论 |
| --- | --- | --- | --- | --- |
| A | 审批人≠申请人 | 服务端拒绝 | service.go:88 校验 | PASS |
| D | 旧版本回执 | 拒绝并记录 | 缺少版本比较 | FAIL |

### 必须修复
1. <文件:行> <问题> → <最小修复建议> → <需补的测试>

### 未验证 / 阻塞
- <原因>
```

结论规则：任一组存在 `FAIL` → 总体 `FAIL`；存在无法取证的检查项 → 该组 `未验证`，总体不得为 `PASS`。

## 失败处理

- 代码不合规：只输出问题、证据与最小修复建议，不擅自改代码；被明确要求修复时，改完必须重跑对应组并重新出表。
- 缺少测试用例：标记 `FAIL（缺测试）`，在"必须修复"中给出用例名与断言要点。
- 无法编译或需求文档缺失：输出 `BLOCKED`，停止检查。

## 完成标准

- A–H 八组全部有结论，每条结论都带 `文件:行` 或命令输出。
- 所有 `FAIL` 项都给出最小修复建议与对应测试。
- 未变更分组已注明"沿用上次结论"及其依据版本。
- 输出可直接粘贴进 `docs/task-09/business-check-report.md` 作为提交证据。
