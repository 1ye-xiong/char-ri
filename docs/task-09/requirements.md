# 题目 09 需求文档：测试车队日志策略的申请、审批、分批发布与结果核查

| 项 | 内容 |
| --- | --- |
| 文档类型 | 需求说明（需求分析阶段交付物） |
| 对应题面 | 《Go 项目业务场景题》题目 09 |
| 版本 | v1.0 |
| 状态 | 已确认：停止权限（4 节）与失败车处理（FR-05）已定稿；其余假设见第 11 节 |
| 业务域 | 车云研发团队的临时诊断日志配置运营（非安全类配置，不涉及驾驶控制） |

## 1. 背景与问题

车云研发团队排障时需要临时提高测试车辆诊断日志的上报频率，但不能一次性对全车队生效：一旦配置有误，全部车辆同时失去原始日志节流，问题反而更难定位。

现状的痛点是**"已下发"被当成"已生效"**：

- 发布动作完成不等于车端应用成功，车端可能应用失败、离线未拉取、回执迟到；
- 车端回执可能重复、晚到，甚至来自错误车辆，若直接覆盖状态，会出现"旧结果盖掉新配置"或"别人的回执算到这台车"；
- 停止活动只能阻止未发送部分，不能让已收到的车端配置消失，必须另起一轮可核查的恢复下发。

产品响应：把一次日志频率调整做成**可审批的配置申请 + 分批（试点→推广）发布活动 + 逐车期望值/实际生效值分离 + 可核查的停止与恢复**的闭环，让每台车的期望值、实际生效值和失败原因都能被解释。

## 2. 目标与可观察结果

- 研发能提交一次带原因、车辆范围和新间隔的申请，并拿到明确的审批结论。
- 运营只能先向 2 台试点车发布，且试点未双双成功时系统不提供推广入口。
- 任何时候系统都能回答三件事：**这台车的期望值是多少、实际生效值是多少、为什么没生效**。
- 停止活动后，系统如实展示"已发/未发"范围和已生效结果，不显示"已撤销"。
- 恢复完成后，逐车可核对是否回到活动前值；只要有一台未确认，就不显示"全部恢复"。

## 3. 范围

### 3.1 P0 范围（本题必须交付的完整闭环）

1. 配置申请：填写原因、五台目标车辆、新日志间隔；退回后修改重提；批准后参数锁定。
2. 审批：负责人批准或退回，审批人不得为申请人。
3. 发布活动：运营创建活动并为本次发布选择 2 台试点车；同车队同时仅一个未结束活动。
4. 试点发布与结果判定：2 台试点全部成功才允许推广；失败或超时则暂停推进。
5. 推广发布：向剩余 3 台发布；逐车记录下发、回执、生效结果。
6. 车端拉取与回执：模拟车辆鉴权后拉取"面向自己的最新已发布版本"，上报成功/失败。
7. 超时显示与迟到回执：60 秒无有效回执显示超时；当前期望版本的迟到成功可更新结果并保留超时历史。
8. 停止活动：阻止未发布部分继续下发，保留已发与已生效记录。
9. 恢复：负责人批准后，运营为曾发布过配置的车辆下发更高的恢复版本，目标为活动前设置。
10. 结果核查：逐车展示发布前值、期望值、生效值、成功/失败/超时/未确认、失败原因；负责人标记活动完成或恢复完成。

### 3.2 不做的部分

- 不做真实车载协议、真实 OTA、固件升级、车队资产管理。
- 不做多车队并行运营、复杂策略条件（速度/区域/时段触发）。
- 不做注册登录全套流程（角色账号预置），但**身份不可通过改请求参数伪装**。
- 不做自动重试与失败车单体重发（见 11 节待确认项）。

### 3.3 固定教学数据

- 1 个车队，固定 5 台车（V1～V5），初始测试数据：V1 在线、V2 离线，其余在线（可在活动中切换在线状态以演示离线分支）。
- 配置项仅 1 个：`logIntervalSeconds`，取值 10～300 的整数秒，初始均为 60 秒。
- 所有车辆在活动前均为 60 秒，视为版本 v1（不是通过本次活动下发的）。

## 4. 角色与权限

预置 4 类身份，服务端按会话身份判定，不信任请求体中的用户/车辆编号。

| 角色 | 标识 | 可做的事 | 不能做的事 |
| --- | --- | --- | --- |
| 研发申请人 | R（如 `rd_wang`） | 创建申请、查看自己的申请、修改被退回的申请并重提 | 审批自己的申请；执行发布/停止/恢复；修改已批准参数 |
| 审批负责人 | A（如 `lead_li`） | 批准/退回申请、决定停止活动、批准恢复、标记活动完成/恢复完成、查看全部核查数据 | 审批自己提交的申请；直接下发配置 |
| 发布运营 | O（如 `ops_zhao`） | 创建发布活动并选试点车、执行试点下发、确认推广、执行推广下发、停止未发送部分、发起恢复下发 | 审批申请、批准恢复、标记完成 |
| 模拟车辆 | V1～V5 各自令牌 | 拉取自己的最新已发布版本、上报自己版本的回执 | 拉取/上报其他车辆的数据 |

权限规则：

- 申请与审批的身份分离在服务端校验：`approverId != requesterId`，同一账号兼任两个角色时该申请拒绝审批。
- 车辆凭证与车辆编号绑定；请求中的车辆编号与凭证不一致一律拒绝（见 FR-07）。
- **停止权限（已定稿）**：试点失败或超时的停止决定由审批负责人下达，运营执行停止操作（负责人也可直接执行）；两种入口都校验操作人具备停止权限，记录操作人、时间与停止范围。停止是对"未发送部分"的发布控制，不是恢复动作，恢复仍需负责人单独批准。

## 5. 核心对象与状态模型

### 5.1 对象关系

```text
配置申请(1) ──批准──> 发布活动(1，同车队同时仅 1 个未结束)
                        ├── 车辆发布记录(5 台车 × 每轮发布，逐车版本递增)
                        │        └── 回执(0..n，按 车辆+版本 幂等去重)
                        └── 活动前基线快照(每车活动前生效值，恢复目标)
```

关键区分（全文统一口径）：

- **下发/发布记录**：系统把某个版本交给车端，只证明"已发出"。
- **期望值**：该车当前最新已发布版本的 `logIntervalSeconds`。
- **生效值**：该车最近一次被接受的成功回执对应的值，才代表"车端已生效"。
- **基线值**：活动创建时快照的各车活动前生效值，作为恢复目标。

### 5.2 申请状态

| 状态 | 含义 | 可执行动作 | 是否终态 |
| --- | --- | --- | --- |
| 草稿 `draft` | 已填写未提交 | 编辑、提交 | 否 |
| 待审批 `pending` | 已提交，等待负责人 | 批准、退回 | 否 |
| 已退回 `rejected` | 被退回，附原因 | 修改后重提（回到 `pending`） | 否 |
| 已批准 `approved` | 参数锁定 | 作为创建发布活动的前置条件 | 否 |
| 已作废 `voided` | 已被活动使用或申请废弃 | 只读 | 是 |

规则：

- 提交时必须包含：原因（非空白，建议 ≤200 字）、五台目标车辆（固定只读）、新间隔（10～300 整数秒）。缺项不得提交。
- 退回后修改重提保留历史版本，重提生成新的申请版本号，原退回记录不覆盖。
- 批准后参数不可原地修改；如需改变间隔，必须新建申请（见 11 节）。
- 一个已批准申请最多创建一个发布活动。

### 5.3 发布活动状态

| 状态 | 含义 | 进入条件 | 可执行动作 |
| --- | --- | --- | --- |
| 待试点 `pilot_pending` | 活动已创建，未下发 | 由已批准申请创建，选定 2 台试点车 | 执行试点下发 |
| 试点中 `piloting` | 已向 2 台试点车下发 | 试点下发成功入账 | 查看进度、停止 |
| 试点通过 `pilot_passed` | 2 台试点均当前版本成功 | 试点判定通过 | 确认推广 |
| 推广中 `promoting` | 已向剩余 3 台下发 | 试点通过后推广 | 查看进度、停止、标记完成（全部成功时） |
| 已完成 `completed` | 5 台车当前期望版本均成功 | 负责人标记 | 只读（可发起恢复，见 11 节） |
| 已停止 `stopped` | 停止未发布部分，保留已发记录 | 运营执行停止 | 批准恢复 → 恢复中 |
| 恢复中 `restoring` | 已向需恢复车辆下发恢复版本 | 负责人批准 + 运营创建恢复版本 | 查看进度 |
| 恢复完成 `restored` | 需恢复车辆全部确认恢复 | 负责人标记 | 只读 |

不变量：

- 同一车队同一时刻最多存在 1 个"未结束"活动（未结束 = 上述除 `completed`、`restored` 外的状态）。第二个活动创建请求直接拒绝。
- 活动在 `pilot_pending`/`piloting` 时，其余 3 台不得收到本次活动的任何配置。
- 停止不删除任何发布记录与回执；`stopped` 不因迟到回执自动回到其他状态。
- `completed` 与 `restored` 必须由负责人显式标记，系统不自动改。

### 5.4 单车发布状态

| 状态 | 含义 | 可见依据 |
| --- | --- | --- |
| 未发布 `not_released` | 本轮未向该车下发（属于"未发范围"） | 无发布记录 |
| 等待确认 `waiting` | 已下发，60 秒内未收到有效回执 | 发布记录 |
| 成功 `success` | 已收到被接受的成功回执 | 发布记录 + 回执 |
| 失败 `failed` | 车端上报应用失败，附失败原因 | 发布记录 + 回执 |
| 超时 `timeout` | 超过 60 秒无有效回执（显示态，非终态） | 发布记录 + 超时事件 |

状态规则：

- "超时"是**展示状态**：当前期望版本的迟到成功回执到达时，状态改为 `success`，同时保留该车的超时事件历史（超时时间、后续成功时间）。
- 失败不改变该车此前生效值；失败后该车也不会因超时判定被改写为 success（只接受新的有效成功回执）。
- 旧版本回执永远不能覆盖新生效值（见 5.5）。

### 5.5 回执判定规则（canonical，全局唯一口径）

每条回执必须带：车辆编号、版本号、结果（成功/失败）、失败原因（失败时必填）、上报时间。服务端按以下顺序判定：

| 序号 | 条件 | 处理 | 是否改生效值 |
| --- | --- | --- | --- |
| 1 | 凭证车辆 ≠ 回执车辆 | 拒绝，记录"跨车回执" | 否 |
| 2 | 该车从未发布过此版本 | 拒绝，记录"未知版本" | 否 |
| 3 | 版本 < 该车当前期望版本（已被更新版本取代） | 拒绝，记录"过期回执" | 否 |
| 4 | 版本 = 当前期望版本，且已有被接受的成功回执 | 记录"重复回执"，不重复记账、不改变结果 | 否 |
| 5 | 版本 = 当前期望版本，成功 | 接受：写生效值、生效时间，状态 `success` | 是 |
| 6 | 版本 = 当前期望版本，失败 | 接受：记录失败原因，状态 `failed`，生效值保持不变 | 否 |

补充：

- 被拒绝的回执全部进入可查询的"被拒绝回执"记录，含车辆、版本、原因、时间，用于核查"为什么这条回执没算"。
- "重复成功不重复记账"：同一车同一版本的成功回执只计一次；重复次数可在记录中体现，不影响任何统计与活动状态。
- 回执只能由该车凭证上报；不允许通过运营页面代填回执。

## 6. 功能需求

### FR-01 配置申请创建与退回重提

- **触发**：研发申请人进入申请页。
- **处理规则**：
  - 目标车辆固定为 V1～V5，只读展示，不可增删。
  - 原因必填；新间隔必须为 10～300 的整数秒，与当前值相同允许提交但页面提示"与当前值一致"。
  - 提交后状态 `pending`，记录提交人与时间。
  - 被退回（`rejected`）时展示退回原因与退回人；申请人可修改原因/间隔后重提，重提生成新版本并保留上一版快照。
- **结果与状态变化**：`draft → pending`；`rejected → pending`（新版本）。
- **权限**：仅申请人本人可编辑自己的申请。
- **异常**：缺原因、间隔越界、非本人编辑、申请已批准后再编辑 → 拒绝并给出具体原因。

### FR-02 审批

- **触发**：审批负责人在待办列表打开 `pending` 申请。
- **处理规则**：
  - 批准：状态 `approved`，记录审批人与时间，参数锁定（服务端拒绝后续修改）。
  - 退回：必须填写退回原因，状态 `rejected`。
  - 申请人与审批人为同一人时，批准/退回按钮不可用，服务端同样拒绝。
- **结果与状态变化**：`pending → approved` 或 `pending → rejected`。
- **异常**：重复审批同一申请（已非 `pending`）→ 提示"该申请已被处理"，不重复记录。

### FR-03 创建发布活动与选择试点车

- **触发**：发布运营对已批准且未被使用的申请点击"发起发布"。
- **处理规则**：
  - 快照当前每台车的生效值作为**基线值**（恢复目标），随活动持久保存。
  - 从 5 台中选 2 台作为试点车，必须为不同车辆；剩余 3 台自动成为推广对象。
  - 校验同车队无其他未结束活动。
  - 展示本活动将使用的间隔值（来自申请，只读）。
- **结果与状态变化**：活动创建为 `pilot_pending`；申请状态 `voided`（已使用）。
- **异常**：活动已存在未结束活动 → 拒绝并提示当前活动；试点车数量不为 2 或重复 → 拒绝；申请未批准 → 拒绝。

### FR-04 试点下发与试点结果判定

- **触发**：运营在 `pilot_pending` 活动点击"开始试点"。
- **处理规则**：
  - 仅为 2 台试点车各生成一条发布记录，版本号在该车当前版本上 +1（初始 v1 → v2），记录期望值、批次=试点、发布时间。
  - 其余 3 台不得产生任何发布记录；其拉取仍拿到原配置（v1，60 秒）。
  - 试点判定：**2 台试点车均为当前期望版本的 `success`** 才视为通过；任一 `failed` 或 `timeout` 则保持暂停推进，推广入口不可用。
  - 判定依据是回执结果，不是"下发完成"。
- **结果与状态变化**：`pilot_pending → piloting`；两台均成功 → `pilot_passed`；否则停留 `piloting`。
- **异常**：试点中重复点击"开始试点"→ 幂等拒绝，不重复生成版本；对非试点车下发 → 拒绝。

### FR-05 推广

- **触发**：运营在 `pilot_passed` 活动点击"确认推广"。
- **处理规则**：
  - 前置校验：试点 2 台仍为当前版本成功（若期间被新版本取代则不满足），否则拒绝推广。
  - 仅向剩余 3 台生成发布记录，版本号为各车当前版本 +1（v2）。
  - 推广不修改试点车的版本与状态。
  - **推广中出现失败或超时（已定稿）**：不提供单台重发，该车保持 `failed`/`timeout`，活动停留在 `promoting` 并展示未确认车辆；负责人可选择停止活动后进入恢复流程，或在未确认项消除前不得标记完成。页面不得隐藏失败车以凑齐"全部成功"。
- **结果与状态变化**：`pilot_passed → promoting`。
- **异常**：未达 `pilot_passed` 直接尝试推广（含接口直调）→ 拒绝并说明原因；重复推广 → 幂等拒绝；对失败车单独重发（接口直调）→ 拒绝并说明"本活动不支持单台重发"。

### FR-06 车辆鉴权拉取

- **触发**：模拟车辆上线后拉取配置（可手动触发"上线拉取"）。
- **处理规则**：
  - 凭证校验通过后，仅返回该车**当前最新已发布版本**（含版本号、间隔值）；该车从未被下发过版本时返回 v1（60 秒）。
  - 离线车在推广期间不会被"推送成功"，只能在其后上线拉取时取得新版本，从而产生迟到回执。
  - 车辆不能拉取他人配置，也不能拉取尚未面向自己发布的版本。
- **结果与状态变化**：产生"拉取记录"（车、版本、时间），不改变生效值；生效值只在回执到达后变化。

### FR-07 回执接收与判定

- **触发**：模拟车辆应用配置后上报回执。
- **处理规则**：严格按 5.5 节回执判定规则执行，成功/失败/重复/过期/未知版本/跨车六种情况都要有可操作的入口与可见结果。
- **结果与状态变化**：接受的成功 → 该车 `success` 并更新生效值；接受的失败 → `failed` + 原因；拒绝 → 不改状态，仅写入被拒绝记录。
- **异常**：无凭证、凭证与车辆不符、缺少版本号或结果、失败原因为空 → 拒绝请求并记录。

### FR-08 超时显示与迟到回执

- **触发**：发布后计时（默认 60 秒，可由教学时钟配置缩短，演示用值需在页面标注）。
- **处理规则**：
  - 计时到期仍无有效回执 → 该车状态显示 `timeout`，记录超时事件（超时时刻、当时的期望版本）。
  - 当前期望版本的迟到成功回执到达 → 状态改 `success`，生效值更新，**超时事件历史保留**并可查看"先超时后成功"。
  - 迟到失败回执同样可记录失败原因；若该车此前已成功则按 5.5 第 4 条处理为重复。
  - 活动已 `stopped` 时，迟到回执可更新该车的逐车结果，但活动状态不变，不自动重启。
- **结果与状态变化**：仅逐车状态与记录变化；活动状态除判定通过/完成外不因迟到回执自动跳转。

### FR-09 停止活动

- **触发**：审批负责人（试点失败/超时后决定停止）或发布运营（执行停止）在 `pilot_pending`/`piloting`/`pilot_passed`/`promoting` 活动点击"停止活动"。
- **处理规则**：
  - 停止只阻止**未发布部分**继续下发：未下发的车辆保持 `not_released`，不再允许向其下发本活动配置。
  - 已下发、已回执、已生效的记录全部保留，页面明确列出"已发（含结果）/未发"两个范围。
  - 页面不得出现"已撤销车端配置""已恢复"等表述；需要恢复必须走 FR-10。
  - 停止后推广入口、试点下发入口全部关闭。
  - 停止权限校验以操作人身份为准，与请求体中的角色字段无关；操作人、时间、当时范围快照写入审计。
- **结果与状态变化**：`pilot_pending | piloting | pilot_passed | promoting → stopped`，记录停止人、时间、范围快照。
- **异常**：对 `completed`/`restored` 活动停止 → 拒绝；重复停止 → 幂等。

### FR-10 恢复

- **触发**：负责人批准恢复后，运营点击"发起恢复"。
- **处理规则**：
  - 恢复对象 = 本活动中**曾发布过配置的车辆**（未发布车辆无需恢复，不生成版本）。
  - 每台需恢复车生成新的发布记录，版本号为该车当前版本 +1（如 v2 → v3），期望值为该车**基线值**（活动前生效值）。
  - 恢复必须是一轮真实下发 + 回执确认，系统不直接改写生效值。
  - 全部需恢复车辆均为当前恢复版本成功 → 可标记"恢复完成"。
- **结果与状态变化**：`stopped → restoring`；负责人标记后 `restoring → restored`。
- **异常**：活动未停止就发起恢复 → 拒绝（已 `completed` 活动的恢复路径见第 11 节 A7）；无任何已发布车辆时恢复入口不可用；未全部确认时"恢复完成"按钮不可用，服务端同样拒绝。
- **页面核对**：逐车展示 基线值 / 当前期望值 / 生效值 / 恢复结果；存在未确认车辆时不得出现"全部恢复"。

### FR-11 结果核查与完成标记

- **触发**：负责人/运营打开活动详情与核查页。
- **处理规则**：
  - 逐车一行，至少包含：车辆编号、批次（试点/推广/恢复/未发布）、发布前值（基线）、期望值、生效值、状态（成功/失败/超时/未确认/未发布）、失败原因、下发时间、回执时间、是否迟到。
  - 提供汇总：已发数量、未发数量、成功、失败、超时/未确认、被拒绝回执数量；汇总必须与逐车明细可互相校验。
  - "标记活动完成"仅在 5 台车当前期望版本全部成功时可用。
  - "标记恢复完成"仅在全部需恢复车辆确认恢复时可用。
  - 页面区分展示"下发数"与"生效数"，不得用下发数代替生效数。
- **结果与状态变化**：`promoting → completed`；`restoring → restored`。
- **异常**：存在未确认项时点击完成 → 拒绝并列出未确认车辆。

## 7. 共享规则

1. **版本**：版本按车辆独立递增，从 v1（初始 60 秒）开始；每次对该车发布产生 v+1，版本号生成需原子，不允许两台并发操作产生相同版本。任何"最新版本"判断以该车当前期望版本为准。
2. **期望值 vs 生效值**：二者分别持久化、分别展示；只有被接受的当前版本成功回执才能改变生效值。
3. **超时**：默认 60 秒，教学时钟可配置（须在页面与文档注明演示值），测试与演示使用同一规则。
4. **幂等**：开始试点、推广、停止、发起恢复的重复点击均不得重复生成版本或重复入账。
5. **身份**：所有写操作按会话身份鉴权；车辆侧按车辆令牌鉴权；请求体中的角色/车辆字段不作为授权依据。
6. **审计**：申请提交/审批/退回、活动创建/试点/推广/停止/恢复/完成标记、每次下发、每条被接受与被拒绝的回执，均记录操作人（或车辆）、时间、前后状态。
7. **一致性**：活动状态必须能由逐车记录推导；不允许出现"活动已完成但存在未确认车辆"或"活动已停止但仍有未发车辆可继续下发"。

## 8. 原型页面要求

原型需可点击/可操作，且覆盖下列页面与状态（状态文案须与本文件一致）：

| 页面 | 必须覆盖的状态 |
| --- | --- |
| 申请页 | 新建、必填校验失败、已提交、已退回（含原因、可改）、已批准（只读锁定） |
| 审批页 | 待审批列表、批准、退回填原因、非申请人审批（按钮不可用） |
| 活动看板 | 待试点、试点中逐车进度、试点通过（推广可用）、试点失败/超时（推广禁用 + 暂停提示） |
| 推广与逐车进度 | 已发/未发范围、成功、失败（含原因）、超时（含超时历史）、迟到成功后状态更新 |
| 恢复结果 | 停止范围快照、需恢复车辆列表、已恢复与未确认区分、恢复完成可/不可标记 |
| 车辆模拟 | 上线拉取（含离线）、上报成功/失败、重复回执、旧版本回执、跨车回执被拒提示 |

## 9. 验收场景与可核查条件

| 编号 | 场景 | 可核查条件 |
| --- | --- | --- |
| S1 正常推广 | 申请 → 审批 → 2 台试点成功 → 推广 3 台 → 逐车核查 → 完成 | 未推广前 3 台无发布记录；推广后 5 台均有版本记录；仅 5 台全部成功时"完成"可用 |
| S2 审批与试点分支 | 申请退回后修改重提；试点一台失败或超时 | 退回原因可见且可重提；试点未通过时推广入口不可用；负责人停止后未试点车无配置、无发布记录 |
| S3 恢复分支 | 部分车辆已生效 → 停止 → 批准恢复 → 更高版本下发 | 停止页显示已发/未发范围且无"已撤销"表述；恢复版本号高于原版本；已恢复与未确认分列，未全确认时无"全部恢复" |
| S4 网络分支 | 离线车晚拉取、旧回执晚到、超时后成功、重复回执、跨车回执 | 生效值不被旧版本覆盖；重复成功不重复记账；超时后成功更新状态并保留超时历史；跨车/未知版本回执被拒并有记录；活动状态不被误改 |
| S5 结果核查 | 同时存在成功、失败、未确认三类车辆 | 逐车列表含基线、期望、生效、状态、原因；汇总与明细一致；活动总状态不能掩盖逐车未确认项 |

补充核查点：

- 重启服务后，申请、活动、逐车版本、回执、超时与拒绝记录仍可查询。
- 用 A 车令牌上报 B 车回执、用运营身份直接改回执、用申请人身份审批自己的申请，三种越权均被服务端拒绝。
- 覆盖率：核心业务包单元测试语句覆盖率 ≥85%，含并发下版本生成与超时判定的可重复并发验证。

## 10. 术语

| 术语 | 含义 |
| --- | --- |
| 试点 | 先向 2 台车发布的活动批次，用于验证配置有效性 |
| 推广 | 试点通过后向剩余 3 台车发布的批次 |
| 生效 | 车端上报成功回执且被服务端接受 |
| 未确认 | 已下发但未取得有效回执（含超时） |
| 基线 | 活动创建时快照的各车活动前生效值，即恢复目标 |
| 恢复版本 | 停止后为曾发布车辆下发的新版本，目标为基线值 |
